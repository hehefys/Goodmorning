## 2.2.1 — 2026-09-18 · 响铃链路四修复（哑响铃 / 划掉不停播 / 主音频不播 / 暂停吞到点）

> 本轮 4 个提交全部集中在响铃链路（`playback/AlarmService.kt` + `util/Constants.kt`）。
> 起因是 2026-09-17 用户连续反馈「今天依旧没有响铃」——排查后发现是**三个独立缺陷叠加**，
> 其中最后一个（暂停吞到点）才是早上没响的真正根因，前两个则是防御性加固 + 各自的回归修复。

### 修复

**1. 哑响铃 —— 响铃卫兵已置位却始终无声**（`e8890ce`）

现象：到点后日志停在「重复 ACTION_RING 到达，忽略（已在响铃）」，之后近一小时无任何播放日志。
服务自认为在响铃、实际没有任何声音，且后续到点全被当作重复忽略，**无法自愈**（11:11:50 点测试键
打印「测试键打断当前响铃」，反证 `ringingGuard` 一直是 `true`）。

根因：`onStartCommand` 中 `ringingGuard` CAS 置位后才 `launch` 起播协程，而该协程首个挂起点是
`settingsRepository.current()`（DataStore `flow.first()` 读盘）与 `repository.playableVideos()`
（Room，`withContext(Dispatchers.IO)`）。协程若静默挂起或被 `serviceScope.cancel()` 取消
（`CancellationException` 被 rethrow，既不触发 crashHandler 也不留日志），卫兵已置位 → 哑响铃。
放大器：兜底 `playFallback()` 内亦调用同一个 `settingsRepository.current()`，主链路与兜底链路一起哑掉。

修复：
- 新增**起播看门狗** `RING_WATCHDOG_MS`：卫兵置位后超时仍未出声 → 判定哑响铃 → 强制走兜底。
- 新增 `readSettingsOrLast()`：读设置加单步超时 `RING_STEP_TIMEOUT_MS`，超时退回上次成功值，
  无缓存则用默认值 —— 主起播与兜底两条链路都不再被同一个挂起点卡死。
- 补诊断日志：起播准备耗时、settings 是否超时、候选视频数。

**2. 划掉通知即停止响铃**（`c7e99a7`）

旧行为是「划掉后立即重建控制面板」（v2 起的有意设计，避免用户误划后失去停止入口）。
用户 2026-09-17 明确改选 **划掉 = 停止本次响铃**：语义更符合直觉（划掉 = 我不听了），
通知内仍保留显式的「停止 / 贪睡」按钮作为常规操作路径。

改动：`ACTION_REPOST_NOTIF` → `ACTION_NOTIF_DISMISSED`；`handleRepostNotification()` →
`handleNotifDismissed()`，逻辑由「重建通知」改为完整收尾 `handleStop()`（停副音频、主音频渐弱、
撤通知、注册明天闹钟、补调度同步）；顺带补上兜底通知此前缺失的 `setDeleteIntent`。

**3. 看门狗误判致主音频永不播放 + 系统铃声兜底在新系统失效**（`6b76854`）

上一修复（`e8890ce`）引入的回归叠加一个既有缺陷，用户反馈「现在主音频都不播放了」。
涉及三个缺陷：

- **看门狗判据错误**：原判据只认 `mainStarted`，但衬托期内「副音频在播、主音频未起」是
  **正常状态**（用户其实听得到声音）。衬托时长与看门狗同为 5s 时同时触发，看门狗抢跑。
  判据改为「**完全没有声音**」（新增 `isAmbientPlaying()`，副音频在播也算已出声），
  看门狗 5s → 8s（覆盖冷启动时副音频从「已启动」到真正出声的窗口）。
- **`fallbackEngaged` 保护性拦截过宽**：`startMain()` 里的 `if (fallbackEngaged) return`
  会让主音频被永久拦下 —— 整场只剩兜底。改为**不拦截**，而在主音频起播时显式
  `stopToneFallback()`：两者走不同音频通道，显式停掉兜底才是正确做法。
- **第三级兜底（系统默认闹钟铃声）在 Android 15+ 实为失效**：ExoPlayer 禁止直接读
  `content://settings/system/alarm_alert`，必然抛 `ERROR_CODE_IO_FILE_NOT_FOUND`，
  一路无声降到第四级蜂鸣。改用 `android.media.Ringtone`（`RingtoneManager.getRingtone()`
  + `Ringtone.play()`）绕开 ExoPlayer 限制；系统铃声纳入 `stopToneFallback()` 统一停音管理。

**4. 暂停吞掉后续到点 —— 09-17「闹钟没响」的真正根因**（`35d3112`）

现象：用户反馈「播放的时候是暂停的，这次播放的是上次暂停的地方，而且并没有播放，直接就是暂停」。

根因：媒体卡「暂停」（`handlePlayPause`）**只静音、不结束响铃场**，`ringingGuard` 仍为 `true`，
于是此后每一次真实到点都落进 `onStartCommand` 的「重复 ACTION_RING 到达，忽略（已在响铃）」
分支被吞掉。`handleStop` / `handleSnooze` 都会 `ringingGuard.set(false)`，**唯独「暂停」这条路径漏了**。

日志铁证（一个暂停场跨夜吞掉五次到点）：

```
09-16 19:23:04  媒体卡操作：暂停播放
09-16 19:24 / 19:25 / 19:28  到点 → 重复 ACTION_RING，忽略
09-17 10:00  到点 → 重复 ACTION_RING，忽略     ← 早上没响
09-17 11:07  到点 → 重复 ACTION_RING，忽略
09-17 11:11:50  测试键打断当前响铃              ← 手动打断才恢复
```

修复：`onStartCommand` 的 `else` 分支新增
`else if (mediaPaused) → forceRestartSession("上一场暂停中，新到点不得被吞")`。
语义澄清：**按「暂停」= 先静音这一声，不等于放弃后续闹钟。**
顺带 `forceRestartSession()` 增加 `reason` 参数（原日志硬编码「测试键打断当前响铃」，
从暂停路径调用会误报）。

用户感知的「接着上次暂停的位置播」：始终是同一个场，`resume()` 自然从暂停点继续；
新一场走 `forceRestartSession` → `player.stop()`（含 `clearMediaItems()`），位置会复位。

### 验收

2026-09-17 19:52 线上实测（安装新 APK 后，进程重启）：

```
19:51:13.981  媒体卡操作：暂停播放
19:52:00.016  到点已由 Receiver 完成去重，直接起播
19:52:00.017  上一场处于暂停态 → 新到点重开一场（暂停不得吞掉闹钟）    ← 修复生效
19:52:05.050  开始播放：file:///.../7686151774852210664.mp4（渐强）
19:52:05.055  选片命中「愿以后的白天有说有笑…」，主音频起播
```

同一次日志中四项改动均有对应验证点（暂停不吞到点 / 主音频恢复 / 看门狗 8s 判据 /
划掉即停止），用户确认「正常了」。

### 教训

- **看门狗的判据必须等价于「用户耳朵能听到」**，而不是某个内部标志位。
- **添加保护性拦截前须确认它不会把正常路径一并拦掉**（`fallbackEngaged` 回归）。
- 「暂停」在响铃场里是**静音**语义，不是**结束**语义；状态机里任何「只静音不结束」的分支
  都要检查响铃卫兵是否需要复位。

  改为 `20201`（规则 `主*10000 + 次*100 + 修订`）。此前该文件长期停留在 `1.0.0`，
  与设置页展示的 `Constants.APP_VERSION` 不一致 —— 系统「应用信息」里看到的是 1.0.0。
- 仓库根目录新增 `LICENSE`（AGPL-3.0）：Gitee 网页端于 2026-08-31 添加的提交 `9b4a116`

## 2026-09-16 · 数据源架构变更：dyproxy 迁至住宅出口（绕过机房 IP 风控）

> 本次**不涉及 App 代码**，版本号不变（仍为 2.2.0）。纯服务端 / 部署架构调整。

### 背景

抖音网页端风控插件 `ArgusSecurityPlugin` 对**机房 IP** 追加了签名校验：从腾讯云服务器直连
`aweme/v1/web/aweme/post/` 一律返回 `403 Blocked by ArgusSecurityPlugin Signature Not Found`，
App 端同步因此拿不到新数据（有本地缓存兜底，不影响响铃）。

实测**同一份 `dyproxy.cjs`、同一条请求**，仅更换出口 IP：

| 出口 | 结果 |
|------|------|
| 腾讯云机房 | 403 `Signature Not Found` |
| 家宽（住宅 IP） | **200**，正常返回作品列表 |

### 变更

- **dyproxy 迁至家里的一台 Ubuntu 24.04 虚拟机**运行，出口为家宽 IP（免风控）。
- 腾讯云 `81.70.52.12` 保留为唯一公网入口，只跑 `frps`（frp 隧道服务端），不再运行 dyproxy 容器；
  原容器已 `docker compose down` 移除，1200 端口改由 frps 绑定。
- 隧道：家里 `frpc` 主动连出到服务器 `7000`，把服务器 `1200` 映射到 VM 的 `1200`。
  **家宽无需公网 IP、无需端口转发。**
- **`dyproxy.cjs` 业务逻辑一行未改。** 仅新增一处便利性改动：环境变量缺失时自动读取同目录 `.env`
  （原先只认环境变量，裸 Node 场景必须先导出 `DOUYIN_COOKIE`）。
- **App 端数据源地址 `http://81.70.52.12:1200` 未改动**，App 无需任何变更。
- 两个进程（`dyproxy`、`frpc`）交由 systemd 托管，`Restart=always` + 开机自启。

### 放弃的方案

评估过逆向抖音 `a_bogus` 签名算法（需移植约 300 行 JS）。放弃原因：该算法与抖音的 JS 混淆版本强绑定
（如 `1.0.1.19-fix.01`），平台一改版即失效，属长期维护负债；且公开参考实现多为教学复刻
（作者自述「如存在纰漏请自行修改」），实测其生成的签名**不被服务端接受**
（带签名与不带签名的报错完全相同）。

### 排查过程中值得记录的两个坑

- **Cookie 粘贴被静默截断**：整串约 6500 字符，网页版终端会截断到 1024 字符且不报错，
  导致缺 `ttwid` 等关键字段而全部 502。**改用 scp / VS Code 传文件**解决。
- **拿免检端点做验证会得出错误结论**：一度用 `notice/count`（查未读数）验证签名，
  该端点**根本不校验签名**，导致"签名已可用"的误判。凡验证某签名/参数是否有效，
  **必须配一条故意去掉该签名/参数的对照请求**。

### 运维注意

- **宿主机（Windows）必须设为不休眠、长期开机** —— VM 随宿主走，宿主休眠则隧道断开。
  闹钟场景的关键时刻是清晨，此点尤为关键。
- 换 Cookie 流程简化：改 VM 的 `/opt/dyproxy/.env` → `sudo systemctl restart dyproxy`
  （不再需要重建容器）。

### 文档

- `dyproxy/README.md` 重写为当前架构（含排查顺序、运维铁律、旧方案遗留说明）。
- 新增 `dyproxy/frp/` 部署包：`README.md`、`frps.example.toml`、`docker-compose.yml`、
  `frpc.example.toml`、`setup-linux-vm.sh`。
- 仓库根 `.gitignore` 新增排除：`dyproxy/.env`、`dyproxy/frp/*.local.toml`（隧道 token 与面板密码）。

## 2.1.3 — 2026-09-11 · 同步链路可靠性加固（「早上播的还是昨天」根治）

### 修复
- **RSSHub 拉取加 callTimeout 45s 总闸**：readTimeout 只管单次读间隔，代理半开连接滴字节会让整次同步无限拖延（实测 12:01 同步发起后无「同步结束」日志直到进程被杀），现在任何拉取 45 秒内必有结果。
- **同步调度 REPLACE → KEEP**：应用启动自检 / 开机恢复不再取消「已到点但被 Doze 推迟、尚未执行」的同步（实测 21:00 档被 21:02 的应用启动吞掉造成漏同步）；仅系统时间被手动修改（TIME_SET）时才强制重算。
- **选片识别「前一晚发布」**：博主固定在前夜 ~23:16 发布次日早安视频，publishDate 永远是「昨天」。新增规则①·补：前一晚 18:00 后发布的最新视频视为当天内容（TODAY）——响铃现场补同步不再每天空跑，日志来源判定与实际发布节奏一致；博主漏发时（最新缓存 >18h 龄）仍会触发补同步。
- **脏数据护栏**：服务器探测发现 dyproxy 对无效/拉取失败的账号会兜底返回另一账号的旧缓存（无效 sec_uid 返回游戏视频，HTTP 200）。同步时若上游最新发布时间比本地缓存最新还旧 24 小时以上，拒绝写入并保留现有缓存，日志明确记录。
- 同步成功日志新增「最新条目标题+发布时间」，便于远程判断数据新鲜度与账号正确性。
- 版本号 2.1.2 → 2.1.3。

## 2.1.2 — 2026-08-31 · 修复闹钟到点被去重逻辑自杀（息屏实测 100% 哑火）

### 修复
- **到点必哑火（致命）**：`AlarmReceiver` 完成去重并记下水位后启动服务，却没把「计划触发时刻」
  传给服务；服务拿 `System.currentTimeMillis()` 兜底去比对，与刚写入的水位只差几十毫秒，
  于是把自己判成「重复到点」直接退出。真机日志实证：11:00:00.012 到点 → 11:00:00.023 被自己判重
  → 11:00:00.030 释放唤醒锁，**全程没有出声**。
  修复：Receiver 启动服务时带上一并置 `EXTRA_DEDUPE_PASSED`，服务见到该标记即跳过二次判重；
  只有在「未经 Receiver 的异常路径」下才在服务端兜底判一次。
- **手动测试键污染判重基准**：主页测试键（force）在 `reset()` 之后又写入了当前时刻，
  导致紧随其后的真实闹钟被判重拦掉。实测：10:58:28 手动测试 → 31 秒后的 10:59 真实闹钟被误杀。
  修复：force 分支只清水位、不写入，手动测试永远不会影响真实闹钟。
- **判重窗口过宽**：同一场闹钟的重复/延迟投递间隔远小于 60 秒，
  窗口从 60s 收到 15s，既拦得住重复投递，也不会误杀用户新设的闹钟。
- **唤醒锁交棒空档**：Receiver 在启动服务成功后立刻放锁、服务 onCreate 再拿，
  中间有一段无人持锁的空档。改为由服务的 onCreate 接管（拿新锁时会同时释放旧锁），
  服务确实没起来时才由 Receiver 自己放锁。

### 内部
- 修正副音频启动日志缺右括号（日志行显示为截断）。

## 2.1.1 — 2026-08-31 · 响铃可靠性：息屏准时 + 异常不卡死

### 修复
- **息屏不响铃**（真机实证：闹钟定 08:01、精确=true，实际延迟到 08:23:53 才补投）：
  调度改为 `setAlarmClock` 优先——官方保证系统永不调整其投递时间、必要时退出低功耗模式；
  降级链 `setExactAndAllowWhileIdle → setWindow → setAndAllowWhileIdle`。
  `canScheduleExact` 兼认 `USE_EXACT_ALARM`（Android 14+ `SCHEDULE_EXACT_ALARM` 默认拒绝）。
- **到点到出声的空档被系统休眠打断**：新增 `RingWakeLock`（`PARTIAL_WAKE_LOCK` 覆盖到点 → 出声）。
- **重复到点叠加播放**：新增 `RingGuard`（设备保护存储记录 triggerAt，60s 内重复到点丢弃，主判重在 Receiver）。
- **Doze 下空等网络**：缓存为空且设备处于 Doze 时跳过现场同步，直走兜底铃声，不再白等 8 秒。

### 加固（QA 观察项 O1）
- 响铃协程新增 `CoroutineExceptionHandler` 兜底：任何逸出的未捕获异常统一降级到兜底铃声，
  每场只降级一次，避免异常循环打转。
- 停止 / 贪睡收尾流程：读设置或续期调度失败也必定撤前台、停服务，
  用户按下的「停止」不会再卡在「通知还在、关不掉」。
- 贪睡注册优先保障：设置读取失败时退回默认间隔，绝不把用户静音丢弃。
- 逐点防护：主音频起播 / 重播 / 副音频起播与重启 / 渐弱收尾 / 蜂鸣循环
  各自 `runCatching` 兜底，单点失败不拖垮整场响铃。
- 副音频起播失败不再拖累主音频——跳过衬托立即起播主音频。
- 服务进前台或播放器创建失败不再让整场响铃崩溃（通知权限被撤等场景）。

### 内部
- 清单补齐 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，receiver/service 标 `directBootAware`；
  通知渠道加锁屏可见 + 免打扰穿透。
- 服务 `startForeground` 先于 ExoPlayer 创建，避免在 Doze 唤醒短窗口内超时。
